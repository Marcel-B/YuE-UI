# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A web interface for YuE Studio (a native macOS app around the YuE2 music model), meant to be used remotely through Tailscale. An ASP.NET Core Minimal API runs YuE Studio's own Python worker as a child process and serves a Vue frontend under `/ui`. README.md (German) is the user documentation. The structure follows `~/repos/YuE_To_Logic` (same SpaProxy/Vite setup, `ClientAppEndpoints`, test style).

## Commands

Requires the .NET 10 SDK and Node.js 22.12+.

```sh
dotnet build                     # whole solution (YueUI.slnx)
dotnet test                      # xUnit (YueUI.Api.Tests with a scripted fake worker, YueToLogic.Core.Tests); no YuE Studio needed
dotnet run --project src/YueUI.Api                      # API on 127.0.0.1:5091 (5090 is the installed app), SpaProxy starts Vite on 127.0.0.1:5174/ui/
dotnet publish src/YueUI.Api -c Release -o publish      # runs npm ci + npm run build, ships wwwroot/ui
deploy/install.sh                # publish + LaunchAgent (de.bvelop.yueui); deploy/uninstall.sh removes it
deploy/install-speech.sh         # the speech lab's Python environment with mlx-audio (--test: one take per model)
```

Frontend only, from `src/YueUI.Api/ClientApp`: `npm run dev`, `npm run build` (vue-tsc, then Vite), `npm run type-check`, `npm run format` (Prettier, config in `.prettierrc.json`; VS Code formats on save through `.vscode/settings.json`). Pass `-p:SkipClientAppBuild=true` to skip every npm step.

## Architecture

### The worker (`Worker/`)

`yue2_worker.py` lives in YuE Studio's installation (`~/Library/Application Support/YuE Studio/src/tools/`), not here. Its protocol is documented at the top of that file: JSON lines in on stdin (`generate`, `render`, `cancel`, `stop`, `quit`, `ping`), JSON events out on stdout (`ready`, `started`, `stage`, `progress`, `song`, `failed`, `idle`, `log`, `error`). Songs are addressed by the absolute path of their `audio.flac`; this app maps that to `run/songN` ids (`SongLibrary.IdFor`). Check that file when YuE Studio updates (its version is in `installed.json`).

- `yueui_worker.py` – the extension the launcher runs in front of the worker (`python yueui_worker.py <yue2_worker.py>`, copied to the output). It imports the worker as a module and patches a few seams (listed in its `SEAMS`, checked against the worker's source at start): extra `generate` fields `full_steps`, `max_tokens` up to 15000, `abc_sampling` and `semantic_sampling`. Songs with different sampling must not share a token batch, which it arranges through `Song.needs_plan` (see `PlanKey`). If a seam changed it runs the worker unpatched and says `"yueui_extensions": false` in the ready event (`WorkerInfo.Extensions`). After a YuE Studio update, run it once by hand and check for `true`.
- `YuePaths` – install root, output dir and the environment the worker needs (`YUE2_OUTPUT_DIR`, `HF_HOME`, `YUE2_ANE_CACHE`, …), copied from what the app passes its own worker.
- `PythonWorkerLauncher` / `IWorkerConnection` – process plumbing; tests replace `IWorkerLauncher` with `FakeLauncher` (`tests/.../TestApp.cs`).
- `WorkerHost` – singleton and hosted service. Starts the worker lazily on the first command, turns events into `SongState`s and a log, and fans changes out to subscribers (bounded channels; a slow subscriber is dropped and its EventSource reconnects with a fresh snapshot). Progress events are throttled per song. Each `SongState` keeps its stages with their start time (`Stages`, via `SongState.Entering`) and whether it is a render (`Render`, remembered from the render command since `started` does not say), which `SongTimeline.vue` shows with how long each stage took. If the process exits, running songs are marked failed and the next command starts a new worker.
- Transcription (SheetSage2) also goes through the worker: `{"cmd": "transcribe", "id", "audio", "task", "offline"}`, answered by `transcribe` events keyed by our id. The worker runs SheetSage2's own Python (`YUE2_SHEETSAGE_PYTHON`, see `YuePaths.SheetSagePython`), which YuE Studio installs; this app does not install it. `TranscriptionEndpoints` stores the upload in a temp folder that `WorkerHost` deletes when the transcription ends; results are read from `<OutputDir>/transcriptions` by `TranscriptionLibrary`.
- YuE Studio runs its own worker (and model) when open; `IStudioDetector` reports that so the UI can warn. Two generating workers can exhaust memory.

### Lyrics (`Lyrics/`)

YuE2 only sings lyrics, it cannot write them. `LyricsWriter` drafts English or German lyrics (`LyricsLanguage`) in YuE2's format from keywords through an OpenAI-compatible server, by default LM Studio (`LyricsOptions`, section `Lyrics`); its system prompt holds the format rules. The default is `google/gemma-4-26b-a4b-qat` (~15 GB). The Mac has 24 GB and that model plus the usual open apps has frozen it in swap (the small `google/gemma-4-e4b` is the fallback), so a lyrics model and YuE2 are never loaded together: no draft while songs are busy, an idle YuE worker is shut down first, the model is loaded through `POST /api/v1/models/load` with `ContextLength` (LM Studio's just-in-time loading may pick the model's maximum context) and unloaded via `/api/v1/models/unload` right after, unless it was already loaded in LM Studio (then it is used and left alone); if LM Studio's guardrail refuses the load ("insufficient system resources"), other loaded models are unloaded, then the context is halved down to `MinContextLength` (the guardrail itself stays on, it is what prevents the freeze); while `LyricsWriter.IsWriting`, songs and renders wait in the `JobQueue`. If the server does not answer, `LmsCli` (`ILmStudioStarter`) runs `lms daemon up` and `lms server start`. The form picks the model from `GET /api/lyrics/models` (LM Studio's native `/api/v1/models` without embedding models, else the OpenAI-style `/v1/models`); a draft names it in `model`, otherwise `LyricsOptions.Model` applies, and the form stores an empty choice for the default so a changed default reaches it. A draft can take a photo (`image`, a JPEG/PNG/WebP data URL the browser scaled down in `photo.ts`) instead of or beside the keywords; it goes to the model as an OpenAI `image_url` part, and the picker marks models whose LM Studio `capabilities.vision` is set (`LyricsModel.Vision`). A draft takes long enough for a phone to lock or a proxy to drop the request, so `POST /api/lyrics` answers 202 and the draft runs in the background; `WorkerHost.UpdateLyrics` keeps its `LyricsState` for the snapshot and publishes `lyrics` events, and the form remembers the id it asked for (`lyricsDraftId`) to take the result even after a reload. A request with `lyrics` and `instruction` revises that text instead of drafting (`LyricsRevision`, `LyricsWriter.RevisionPrompt`: change only what was asked, keep the rest word for word); the form offers it under the lyrics field and keeps the previous text in memory for an undo. Tests fake LM Studio through the named `HttpClient` (`FakeLmStudio` in `TestApp.cs`).

### Logic export (`Logic/`, `LogicEndpoints`)

`GET /api/songs/{run}/{song}/logic` converts the song's `score.abc` (`IScoreConverter`) and writes it with its `audio.flac` into a `.logicx` package (`ILogicProjectWriter`, `ZipLogicPackageSink` into a self-deleting temp file, since `ZipArchive` writes synchronously), in this process; warnings go in the `X-YueToLogic-Diagnostics` header (compact JSON of `Diagnostic`), a song that cannot become a project answers 422 with its errors. `LogicOptions` (section `Logic`) only has `SplitSections`. The way back is `POST /api/midi/abc`: a MIDI file (typically a song edited in Logic) goes through `IMidiToAbcConverter` and comes back as `MidiScore` (`abc` plus its warnings), which the library puts into the form with the song's style, lyrics and seed, or the advanced parameters as a bare score. The browser fetches the ZIP instead of following a link, so a refusal becomes a message and the warnings are readable. The tests run the real library.

The Logic page (yue-to-logic-pro's former web app) works from a library song (`song` = `run/songN`, the server reads its files) or an uploaded `score.abc` (+ optional FLAC): `POST /api/logic/convert` answers the `ConversionResult` (score with notes, MIDI as base64) for its preview, `POST /api/logic/export` the ZIP with its options, `splitSections` and `instruments` (track → name, port, channel; the export puts the track on that channel and, for outputs the template knows, on an External Instrument). These answer in `YueToLogicJsonContext`'s JSON (enums by name, `Warning`, `DrumMachine`), not this API's camelCase enums, because the page's frontend was written against it; `Instrument.Kind` carries its converter on the property since the global converter would win over one on the type. The instrument library (`SqliteInstrumentStore`, tables `instruments`, `track_assignments`; `InstrumentEndpoints`, same routes as yue-to-logic-pro) and the page's presets (`SqliteLogicPresetStore`, `logic_presets`, form kept as opaque JSON, names matched through an upper-cased `name_key`) are schema version 7. `POST /api/logic/import` takes over what yue-to-logic-pro's server kept (its `GET /api/instruments`, `/instruments/assignments` and `/presets` answers in one object), matched by name so it can run twice.

The preview's browser sound is a small synthesizer (`logic/synth.ts`: two oscillators, the `square` one a pulse with width and PWM built from a sawtooth minus its delayed copy since Web Audio has no pulse wave, noise, filter, amp and filter ADSR, LFO), played for every pitched note routed to the browser; drums keep their noise kit. A patch is opaque JSON to the server (`normalizePatch` fills and clamps it in the browser). Each track's sound (`track_synths`, by track name) and named sounds (`synth_presets`) live in `SqliteSynthStore` (schema version 8, `SynthEndpoints`, `/api/logic/synths/...`); a track keeps a copy, so changing a named sound changes no track. `logic/synths.ts` holds both for the page, `SynthDialog.vue` edits them, and the output pool looks the patch up per note, so an edit is heard at once. It never reaches the MIDI file or the Logic project. Every track has a channel strip in the browser output (fader, `StereoPanner`, `AnalyserNode` for the meter) before the master; `MixerPanel.vue` sets volume and pan through `OutputPool.mixChanged` without touching the schedule, and reads the meters from `OutputPool.levels`. Its settings are one JSON row (`logic_mixer`, schema version 9, `/api/logic/synths/mixer`). Mute is the routing's `muted`, solo is kept in the page only; both take notes out of the schedule, so they apply to MIDI ports too.

The preview also shows and plays the song's recording (`logic/recording.ts`): the library song's `audio.flac` (fetched from `/api/songs/{run}/{song}/audio`) or the uploaded FLAC is decoded once in the browser into 5 ms peaks, drawn as a lane of its own above the tracks (`pianoRoll.ts`, `WAVE_HEIGHT`) and played on its own `AudioContext` from the playhead, starting at `ScoreDocument.CountInTicks`. Switched off (per browser, `loadRecordingSettings`) nothing is fetched. `POST /api/logic/musicxml` answers the converted score as MusicXML (`IMusicXmlWriter` in the Core).

The analyzers (`spectrum.ts`, `SpectrumBars.vue`): every place that plays in the browser registers a `SpectrumSource` (its `AnalyserNode`s, one per audio context since nodes cannot cross contexts, and its `playing` ref). The player routes its element through a `MediaElementSource` only when its analyzer is on, and only from a click (`player.ts` `listen`): iOS starts a context made outside one suspended, and a routed element then plays silence; it also sets `navigator.audioSession.type = 'playback'` so Web Audio keeps playing with the screen locked. The small analyzer in `PlayerBar.vue` is also the button (`VisualsButton.vue`) for the switches; the Logic preview has a large one fed by `OutputPool.analysers()` and `RecordingPlayer.analyser`. `AudioBackground.vue` (setting `background`, off by default, never under `prefers-reduced-motion`) moves three glows behind the cards through transform and opacity only; `#app` has `isolation: isolate` so its `z-index: -1` stays above the body's background. The switches are per browser (`yue-ui.visuals` in `localStorage`).

### YueToLogic.Core (`src/YueToLogic.Core`)

Moved here with its history from yue-to-logic-pro (its API, CLI and the StemMyWav/ChangeMyVoice clients were left behind; this app has its own). It stays host-independent: no console, file system or logging, input is a `string`/`Stream`, output `byte[]` or a caller-supplied `Stream`, problems are `Diagnostic` records with stable codes `YTL0xx` (`DiagnosticCodes`; add a code, never reuse one) instead of exceptions. It is `IsAotCompatible`, so JSON goes through the source-generated `YueToLogicJsonContext`. `AddYueToLogic()` registers everything as stateless singletons.

- Pipeline (`ScoreConverter`): `ConversionOptionsValidator` → `AbcScoreParser` (YuE2's ABC dialect, lenient; an accidental holds for its letter in every octave until the bar line) → `ScoreArranger` (octave shifts, doubling, generated chords/bass/drums/guide tones, groove, mono, count-in; order documented in the class) → `MidiRenderer` (DryWetMidi, type 1). Track names (`Vocal`, `Ins`, `Chords`, `Bass`, `Drums`, `Guide`, …) key channels, programs, instruments and Logic template tracks alike.
- The way back (`MidiToAbcConverter`): `MidiFileReader` → track roles by name → sixteenth grid → `ChordTrackReader`/`ChordRecognizer` → `AbcScoreWriter`, which lays the score out exactly as YuE2 does; the tests hold it to character-for-character round trips of `samples/score.abc` (the official YuE2 example, copied into both test projects as `Samples/score.abc`).
- MusicXML (`MusicXml/MusicXmlWriter`): partwise 4.0, one single-voice part per track except the drums, cut into slices at every bar line and note start or end so overlaps become chords with ties; chord symbols (`harmony`), sections and tempo above the first part. Checked by `MusicXmlWriterTests` (every measure adds up to its bar) and once by opening the sample in music21, not yet in MuseScore.
- Logic writer (`Logic/`): Logic's format is undocumented. `LogicProjectWriter` patches a template saved by Logic Pro 12.3 (`Logic/Template/*`, embedded); its partial-class files record byte offsets and how they were derived in their `<remarks>`, keep that style. The template decides which tracks exist (`YTL053`); routing a track to hardware swaps in Apple's External Instrument, only for MIDI outputs the template's Mac knew (`YTL055`). `LogicProjectWriterTests` checks the template's own song reproduces Logic's note bytes exactly; a new template must be saved from Logic, plists converted with `plutil -convert xml1`, and that test updated. Every change was verified by opening the result in Logic; there is no other oracle. Audio must be 48 kHz FLAC (mix) / WAV (stems).

### Voices (`Voices/`, `VoiceEndpoints`)

A finished song can be sung again with a reference voice: `StemClient` sends its FLAC to StemMyWav's Mac API (`POST api/separate?model=&dereverb=true`, synchronous, answers a ZIP with `vocals_dry.wav`, `vocals_reverb.wav`, `instrumental.wav`), `VoiceClient` sends the dry vocals to ChangeMyVoice (`/api/v1/jobs`, polled, since its webhook would need a reachable callback) and `FfmpegMixer` (`IAudioMixer`) mixes the result at the original vocals' mean volume back under the instrumental, optionally with the reverb stem, as a 48 kHz FLAC. Both services run on the same Mac; their gateways on Proxmox are not used. `VoiceOptions` (section `Voice`): ChangeMyVoice's `BaseUrl` and key (`ApiKey` or `ApiKeyFile`), StemMyWav's `StemsBaseUrl` and key file. Reference voices live only in ChangeMyVoice (the same collection yue-to-logic-pro edited); the page `VoicesPanel.vue` lists, plays, uploads and deletes them.

The result is a version (`VersionState`), a file of this app's own under `versions/` next to the database with a row in `song_versions` (`SqliteVersionStore`), never written into YuE Studio's song folder. The row keeps what the version was made with (voice, shift, strength, steps, reverb and the stem model, which is taken from `VoiceOptions.StemModel` when it is asked for and used for it even if the setting changes later); the library shows that under each version. `SongLibrary` lists a song's versions in `SongInfo.Versions` and deletes them with the song. `VoiceConverter` is a hosted service with a queue that makes one version at a time, and only while neither the YuE worker nor `LyricsWriter` is busy: it shuts down an idle worker first, and while `IsConverting` songs, renders and lyrics wait in the `JobQueue`, like they do for the lyrics writer (24 GB are not enough for YuE2, separation and Seed-VC together). Progress goes through `WorkerHost.UpdateVersion` as `version` events and into the snapshot; `PushNotifier` announces finished ones. After a restart, queued versions are queued again and half-made ones marked failed. The player plays a version as a `Track` with its own `src` and `songId` pointing at the song, so rating, playlist and the song's address stay the song's. A voice can also be chosen in the form (`GenerateRequest.Voice`, looked up when the song is asked for and carried as `SongVoice` in the queued job's payload, `JobQueue.VoiceKey`, and via `WorkerHost.ExpectSongs(voice)` onto the started songs' `SongState.Voice`); `AutoVersions` (hosted service, subscribes like `PushNotifier`) queues a version for each such song once it is ready. Renders never carry a voice. Only whole octaves are offered in the UI: any other shift sings out of key over the song's own accompaniment.

The voices page also splits songs into stems (`StemEndpoints`, `StemsPanel.vue`), which needs only StemMyWav (`VoiceOptions.StemsConfigured`, `VoiceInfo.StemsConfigured`). A `StemSetState` waits in `VoiceConverter`'s queue (entries `stems:<id>`, same memory rules as a version), `StemClient.ExtractAsync` keeps every WAV of the ZIP whatever the model makes, `WavPeaks` reads each one's waveform on the server (one scale per set, so the phone need not download stems to draw them), and `IAudioMixer.EncodeFlacAsync` stores it as 24-bit FLAC (the WAV where ffmpeg fails) in `stems/<id>/` next to the database (`SqliteStemStore`, `song_stems`, schema version 10). The model list is StemMyWav's `GET api/models`, or only `StemModel` when that does not answer. Progress goes out as `stems` events and in the snapshot's `Stems`; `#/voices/<run>/songN` preselects a song. Tests fake both services through the named `HttpClient`s (`FakeVoiceService`, `FakeStems` in `TestApp.cs`) and the mixer (`FakeMixer`); `AudioMixerTests` runs the real ffmpeg when it is installed.

### Speech lab (`Speech/`, `SpeechEndpoints`)

A page for trying local text-to-speech models (a podcast is the idea; YuE2 only sings). `SpeechLab` (hosted service, like `VoiceConverter`) speaks one take at a time: a text, a model from `SpeechOptions.ResolvedModels` (`SpeechModel.Defaults`: Chatterbox Multilingual v3, Qwen3-TTS, Higgs Audio v2/v3, MOSS-TTS Local, all mlx-audio repos, replaceable under `Speech:Models`) and optionally a recorded voice to clone (`SpeechVoice`, 24 kHz mono WAV plus its transcript, which several models need). `MlxAudioEngine` (`ISpeechEngine`; tests use `FakeSpeech`) runs `Speech/yueui_speech.py` with the lab's own Python (`Speech:Python`, made by `deploy/install-speech.sh`, not YuE Studio's) once per take, so the model leaves the memory with the process; the script answers `YUEUI {json}` lines (stage, done with timings and peak memory) between mlx-audio's own output, whose `Error …` line becomes the take's message. Models download into `Speech:ModelCache` (`HF_HOME`) on their first take. Browser recordings (WebM or MP4) go through ffmpeg (`PrepareVoiceAsync`: silence cut at both ends, 30 s at most). Memory: a take waits while the worker is busy, `LyricsWriter.IsWriting` or `VoiceConverter.IsConverting`, shuts an idle worker down, and while `SpeechActivity.IsSpeaking` (a class of its own, since the converter and the lab would otherwise depend on each other) `JobQueue`, the lyrics writer and `VoiceConverter` wait; each side claims its flag before looking. Takes and voices are in `speech_takes`/`speech_voices` (schema version 11, `SqliteSpeechStore`), files in `speech/` next to the database. Progress goes out as `speech` events (`WorkerHost.UpdateSpeech`, not in the snapshot); `SpeechLab.vue` loads `GET /api/speech` when shown and when the stream reopens and lays the events over it.

### Queue (`Queue/`, `QueueEndpoints`)

`JobQueue` (hosted service) takes every song, render and lyrics draft instead of refusing it with 409 while another model holds the memory: songs and renders go to the worker (which queues and batches them itself) as soon as neither `LyricsWriter.IsWriting` nor `VoiceConverter.IsConverting`; a draft also needs the worker idle. Jobs start in order, bundled by model in one respect: while YuE2 is busy, songs and renders pass a draft waiting at the front and go to the worker (it batches them), until that draft has waited `QueueOptions.BundleWindow` (section `Queue`, default 20 min); a version waiting that long in `VoiceConverter` (`WaitingSince`) holds back new songs the same way. A job that can start at once is started inside the request, so a missing YuE Studio still answers 503; otherwise the request answers 202 with the `QueuedJob` (a draft with its `LyricsState` in stage `queued`, whose id the form keeps as `lyricsDraftId`). Waiting jobs are in `queued_jobs` (`SqliteJobStore`, job and payload as JSON) and resume after a restart; `WorkerHost.UpdateQueue` puts them into the snapshot and `queue` events, `QueueList.vue` shows them with move and remove, each with why it waits (`queueModels.ts` mirrors the queue's rules, counting down the window from `StatusSnapshot.BundleWindowSeconds`), under `QueueOverview.vue`, one line with the three models and which holds the memory. The memory checks race each other, so each side claims before it looks: `WorkerHost.ExpectSongs` counts a command as busy from before it is sent until its `started` event (the lyrics writer or a conversion would otherwise shut down a worker that has a command in its pipe), while `LyricsWriter` and `VoiceConverter` take their flag first and then look at the worker. Voice versions keep their own queue in `VoiceConverter`; transcriptions are not queued.

### Sharing (`Share/`)

`GET /api/songs/{run}/{song}/share` encodes the song's FLAC into a 128 kbit/s AAC (`.m4a`) in a self-deleting temp file, through `IAudioEncoder` (`AacEncoder`: macOS's own `afconvert`, else `ffmpeg`; 501 without either; tests use `FakeEncoder`). The frontend's `share.ts` hands it to the Web Share API; Safari refuses `navigator.share` once the tap is a few seconds old, so on `NotAllowedError` `ShareDialog.vue` (one, in `App.vue`) offers a second tap. Without file sharing (desktop browsers) the file is downloaded.

### Notifications (`Push/`)

Web Push, so a phone hears when a song, transcription or lyrics draft finishes (on iOS only the home-screen app, over HTTPS). `PushNotifier` is a hosted service that subscribes to `WorkerHost` like a browser (`Subscribe(checkStudio: false)`) and sends on the change to finished, cancelled songs excepted; texts in `PushTexts` (de/en per subscription, not `i18n.ts`, since no page need be open). `PushStore` keeps the VAPID key pair and subscriptions in `push.json` (`PushOptions`), made on first use; a new key pair orphans every subscription. `WebPushSender` (`IPushSender`, Lib.Net.Http.WebPush) drops subscriptions the service answers 404/410 for; tests replace it with `FakePushSender`. Frontend: `public/manifest.webmanifest`, `public/sw.js` (shows every push, Safari revokes silent ones; no fetch handler, so no stale build is cached), `push.ts` and `NotificationButton.vue`. The home-screen app on iOS resumes from memory instead of reloading, so it would run an old build until closed: `vite.config.ts` (`buildVersion`) compiles a build id into the app and writes it to `version.json`, and `update.ts` compares them when the app becomes visible and on every snapshot (a deploy restarts the server), then `App.vue` offers a reload; in standalone mode a refresh button sits in the menu bar.

### Playlist and database (`Data/`, `PlaylistEndpoints`)

The app's own state lives in one SQLite file (`DataOptions`, section `Data`, default `yueui.db` next to `push.json`), opened by `SqliteDatabase`, which creates the file on first use and versions the schema with `PRAGMA user_version` (add a step, never edit an old one; same pattern yue-to-logic-pro used). It holds the playlists (`SqlitePlaylistStore`): a row each in `playlists`, their song ids in `playlist_songs`, at least one always (the last cannot be deleted, so "add to playlist" has somewhere to go); titles given to runs (`SqliteRunTitleStore`, `run_titles`); and song ratings, 1 to 5 stars per song id (`SqliteSongRatingStore`, `song_ratings`, no row when unrated). `SongLibrary` lays the ratings into `SongInfo.Rating` and forgets them with deleted songs; `PUT /api/songs/{run}/{song}/rating` publishes a `library` event, and the frontend keeps an optimistic copy in `ratings.ts` for the library and the player. A rename (`PUT /api/runs/{run}/title`) never touches the folder, since its name is the song id that playlists, links, the worker's states and YuE Studio rely on; `SongLibrary` lays the title over the worker's (`RunInfo.OriginalTitle` keeps that one) and `WorkerHost.RunRenamed` renames the queue's songs. `SongLibrary` still lists songs when the database cannot be read. `PUT /api/playlists/{id}/songs` replaces a playlist's songs as a whole and only accepts ids of existing songs; `GET /api/playlists` leaves out songs deleted since. Which playlist a page shows (and a single tap adds to) is chosen per browser (`playlist.ts`, `localStorage`); with more than one, the plus by a song (`PlaylistToggle.vue`, library and player) opens a menu of them. On the server rather than in `localStorage`, because the phone's home-screen app, its Safari and the Mac each have their own storage.

### API

Minimal API, endpoint groups per file: `WorkerEndpoints` (status, SSE via `TypedResults.ServerSentEvents`, generate, render, cancel, stop, worker shutdown), `TranscriptionEndpoints` (upload up to 300 MB, list, cancel, score, ZIP, delete), `LyricsEndpoints` (lyrics drafts), `PushEndpoints` (VAPID key, subscriptions, test push) and `LibraryEndpoints` (library listing with sizes, FLAC with range processing, score, ZIPs per song and per run built in a self-deleting temp file, deleting songs and runs, free space). Deleting is refused (409) while this server's worker is on the song (`WorkerHost.IsWorkingOn`) and publishes a `library` event so every open browser reloads. `SongLibrary` reads run folders and only accepts names matching the worker's patterns, which is also the path-traversal guard. Commands to the worker answer 202; the result arrives as events. JSON is camelCase with enums as camelCase strings. The server binds to 127.0.0.1 only; remote access is `tailscale serve --https=8443` (443 on this Mac already proxies another service), there is no login.

### Frontend (`src/YueUI.Api/ClientApp`)

Vue 3 + TypeScript + Vite, no router, no state library. `App.vue` holds the state and the event subscription and switches pages (`view.ts`: create, transcribe, songs, playlist, voices, logic, lab, kept in the URL hash, shown with `v-show` so a page keeps its input; a song's address is `#/songs/<run>/songN`, which scrolls the songs page to it and marks it, and player, playlist and queue link there; `#/logic/<run>/songN` opens a song on the Logic page) through a PrimeVue `Menubar`; `player.ts` owns the one audio element (in `PlayerBar.vue`, outside the pages, so playback survives a page change) and what plays next; `playlist.ts` holds the playlists and the active one; `api.ts` is the only place that talks to `/api`, apart from the Logic page's own `logic/api.ts`; `types.ts` mirrors the API's records by hand; `i18n.ts` holds every German and English string; `form.ts` maps the form to `GenerateRequest` and keeps it in `localStorage`, and a song's `request.json` (`GET /api/songs/{run}/{song}/request`, `SongRequest`) back into the form for "as a new song" (`SongMenu.vue`). `styleTags.ts` holds the style building blocks (`StyleBlocks.vue`), picked from YuE v1's `top_200_tags.json` plus language and tempo, and inserts or removes them in the comma-separated style. `abcTranspose.ts` transposes a score by semitones in YuE2's dialect (an accidental holds for its letter in every octave until the bar line, as in `YueToLogic.Core`'s `AccidentalTracker`) and respells it in the new key; the − and + by the score field and its key picker (`transposeToKey`, the shorter way) use it, since the model sings the `Vocal` voice at its written pitch. `search.ts` filters the library in the browser (the listing already carries style and lyrics), in title and style or in the lyrics, never both, since common lyric words would bury the title hits. `sort.ts` orders it (date, stars, duration; a run keeps its songs together and moves by its best one), remembered per browser in `localStorage`. The Logic page (`LogicPage.vue`, `components/logic/`, `logic/`) is yue-to-logic-pro's page ported: options, presets, instruments, a piano-roll preview and playback through Web MIDI (`logic/midiPlayer.ts`, Chromium only) or Web Audio; it is loaded with `defineAsyncComponent` and mounted only once opened, so a normal visit does not fetch instruments or presets. Mobile first (the main client is a phone): inputs are 16px to avoid iOS zoom, the player uses `preload="none"` and starts `play()` inside the click, which iOS requires.

UI components come from PrimeVue 4 (styled mode, Aura preset from `@primeuix/themes`), configured and registered globally in `main.ts`, except those only the library needs (`DataView`, `Fieldset`, `Dialog`), which `LibraryList.vue` imports itself so they load with it after the first paint (`defineAsyncComponent` in `App.vue`). Import from `primevue/<name>`, never the `primevue` barrel. `primevueStyles.ts` stops PrimeVue from clearing its list of loaded styles on every component update (each clear made the next update rewrite its `<style>` and restyle the whole page; Safari reloaded the page for its energy use); remove it only once PrimeVue no longer does that. `theme.ts` is Aura with only the design tokens of the components in the bundle, since the full preset carries all ~100; a component used for the first time needs its entry there, and `vite build` fails naming it otherwise (`presetCoversStyles` in `vite.config.ts`). Use a PrimeVue component (`Button`, `Card`, `InputText`, `Rating`, …) instead of styling native elements; adjust the look through the preset's design tokens rather than by overriding `.p-*` classes. `style.css` keeps only the page frame, the app's colour variables (`--accent`, `--text`, `--surface-sunken`, …, mapped onto Aura's tokens so scoped styles share PrimeVue's palette in both themes) and the text helpers `.muted` and `.danger` plus the Logic page's `.hint`; the old `.button`, `.card`, `.link`, `.field` and native input rules are gone, so a text field that should fill its row needs `fluid`. Layout goes into Tailwind utilities, or a component's `<style scoped>` when it is more than a few classes.

Tailwind CSS 4 (via `@tailwindcss/vite`, without preflight) with `tailwindcss-primeui`, which adds utilities for PrimeVue's tokens (`bg-primary`, `text-muted-color`, `bg-emphasis`, …). Cascade layers decide what wins, in this order (declared at the top of `style.css`): `theme, base, primevue, components, utilities`. So utilities override PrimeVue, and PrimeVue overrides the app's own element rules in `base`. Keep global CSS inside a layer; an unlayered rule, including every `<style scoped>` block, beats all of them.

## Conventions

- Commit messages and branch names are German; code, comments and API messages are English. UI strings exist in both languages in `i18n.ts`.
- Comments explain why. New API fields go into the C# record, `types.ts` and, if user-facing, `i18n.ts` together.
